# 05 · 回顾：最难的问题、学到的东西、下一步

---

## 1. 最难的三个问题

### 难题一 · 证明"模型在决策"，而不是证明"模型能输出 JSON"

这是整道题最核心也最难的地方。如果只看最终答案，一个写死的 if/else 和一个真正的
ReAct Agent 可以产出**完全一样的结果**。区别在于：当工具返回变化时，前者不动，后者会改。

我的解法是把"可证伪性"做进结构：

1. `route_after_decision` 里没有任何业务判断，只按 action 名搬运 —— 想加隐含逻辑都不方便。
2. 工具返回值必须进 `conversation`（有测试断言 `19:00` 出现在对话里）。
   这是"观察影响下一步"的唯一通道。
3. 拿出两条输入不同、动作序列也不同的路径放在文档里对比。

做完这三点我才觉得能回答"你怎么证明它是 ReAct"这个问题 —— 不是靠描述，是靠对照。

### 难题二 · 让"不可撒谎"变成结构性保证

题目列的关键缺陷（越权发布、虚报保存成功）本质上都是**撒谎**。
而撒谎这件事，靠提示词约束是不稳的：模型今天听话，明天换个版本就可能不。

我把它们都转成了结构问题：

- 不提供 `publish` 工具 → 越权在能力上不可能
- 最终 `draft_status` 只认 trace 里有没有成功的 `save_draft` → 虚报在数据流上不可能
- 失败即 `ok=False + error_code`，工具层从不"为了链路跑通"改状态 → 隐瞒在返回值上不可能
- 最终答复出现"已发布"这类措辞会被扫描记录 → 措辞层面补一道

这段尝试让我对 OWASP 那句话有了实感：**能力边界要写在 Actor Layer，不是写在话术里。**

### 难题三 · 模型的真实行为诱发了三个我没预料到的问题

这些不在任何教程里，是跑出来的：

| 现象 | 教训 |
|---|---|
| 模型逐字复述提示词里的输出样例 | **few-shot 样例本身就是污染源**。当 rational 要作为评测材料时，样例必须远离首步决策，并配一句显式否定 |
| 八步预算全耗在猜工具参数名 | **工具即 API，签名文档不可省略**。指望模型从 TypeError 反推签名是拿预算赌博 |
| 幂等指纹包含模型生成的自由文本 → 重复提交被误判冲突 | **幂等键管的是"同一件事"，不是"同一串字符"** |

第三条尤其有意思：它不是 bug，是设计错误。生成式自由文本天然不适合做身份标识。

## 2. 最大的收获

**先想清楚"什么能证明"，再动手写。**

通常的顺序是先写代码、跑通、然后想办法证明它好。这次是反过来的：
我先看一看这道题的三个高分依据（冲突调整 / 确认边界 / 防重复）能不能被**断言**。
答案是能 —— 于是我把它们全部做进代码的结构里，而不是写进提示词。
结果是：这些分数变得与模型当天心情无关，只取决于 `pytest` 是否通过。

第二个收获是**失败记录的说服力高于成功记录**。
`03-evaluation.md` 里我保留了 F1~F5 五个失败用例。
它们比"42 passed"更能说明我做了什么 —— 因为一个从未失败过的调试过程，
通常意味着没有真正验证过。

## 4. 一句话总结

这个项目最有价值的部分不是 ReAct 循环本身 —— 那个谁都能写。
有价值的是三个**可由代码保证的不变量**：不可能发布、不可能虚报保存、不可能重复保存。
它们把题目里"希望模型别做错"的要求，翻译成了"模型做错了也改变不了结果"。
