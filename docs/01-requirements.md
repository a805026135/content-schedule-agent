# 01 · 需求：用户、目标、范围与成功标准

> 题目原文复述见仓库根目录 README。本文件回答的是：**在题目的约束下，
> 我给自己定了一条什么样的线，以及怎么判断有没有过线。**

---

## 1. 用户与目标

| 项 | 内容 |
|---|---|
| **使用者** | 内容团队的排期负责人（一个人或一个小组），负责把已制作完成的素材安排到发布时段 |
| **当前痛点** | 素材的资质信息（版权、肖像、审核归档、文案合规）散落在不同地方；排期表多人共用，容易发生撞档；口头确认过的事情没有留痕 |
| **要达成的效果** | 对每个待处理素材给出一句话就能执行下去的结论：**能不能排、什么时候排、还差什么、等你确认什么** |
| **明确的非目标** | 不替用户做决策，不替用户发布，不做素材本身的剪辑或生成 |

一句话版成功标准：

> **排期负责人在拿到输出后，不需要再追问"那到底几点发"或"这个是不是能发"。**

## 2. 题目的六条「必须验收」与对应的硬性要求

| # | 验收点 | 本项目的具体标准（可断言） |
|---|---|---|
| 1 | 正常排期 | 素材字段完整、规则 `pass`、时段空闲 → `audit_status=passed`，`suggested_slot` 等于用户要求的时段，`draft_status=saved` |
| 2 | 素材信息缺失 | 必填字段缺失 → 触发 `request_clarification`，**不得自行编造字段值**，`draft_status=not_saved` |
| 3 | 规则风险 | 命中 `risk`/`warn` → `audit_status=risky`，`pending_confirmations` 非空；命中 `block` 的素材不得进入排期 |
| 4 | 时段冲突 | 用户要求的时段被占用 → `suggested_slot` 给出另一个**确实可用**的时段，`pending_confirmations` 非空，**不得声称用户已同意改期** |
| 5 | 重复提交 | 同一 `request_id` 重复执行 → `draft_id` 不变，`total_drafts` 保持 1，第二次标记 `duplicate=true` |
| 6 | 保存失败 | 注入存储失败 → `draft_status=not_saved`，`failures` 里含 `TOOL_UNAVAILABLE`，**不得出现任何暗示成功的措辞** |

除此之外，试卷对通用能力的要求也被纳入验收：

| 试卷要求 | 本项目落点 |
|---|---|
| 模型选动作 → 执行工具 → 观察 → 调整的循环 | `src/agent/graph.py`：`decide → execute/clarify → decide` |
| ≥2 条差异化路径的运行记录 | `examples/real_llm/case04_slot_conflict/`（冲突）与 `case02_missing_info/`（信息缺失） |
| trace 含步骤/参数/返回摘要/后续动作/决策依据 | `ToolCallRecord` schema，`next_action` 在 finalize 回填 |
| 步数或工具调用上限 + 明确的未完成状态 | `max_steps` / `max_tool_calls`；超限返回 `MAX_STEPS_EXCEEDED`，CLI 退出码 `2` |
| ≥3 组输入覆盖正常 / 资料不足 / 工具失败 | `examples/real_llm/` 下 7 组，含 `case07` 超限 |

## 3. 范围边界

### 做

- 素材元数据读取与缺失字段识别
- 数据驱动的规则检查（`block` / `risk` / `warn` / `pass`）
- 时段可用性查询与替代时段建议
- 草稿的幂等保存
- ReAct 决策循环与完整 trace 落盘

### 明确不做（与 Documentation 保持一致，避免评审误判为"没做完"）

| 不做的事 | 原因 |
|---|---|
| **任何形式的发布** | 题目明文要求"仅保存草稿"。本项目从工具集合上去掉了发布能力，不是因为没时间，而是防止越权的最强手段 |
| 真实的排期系统对接 | 题目要求业务工具可用本地函数或 Mock |
| 多 Agent 协作 / 线上部署 / 图形界面 | 题目明文写到"界面、线上部署、多 Agent、生产级 Runtime 均非必需" |
| 向量检索、语义匹配 | 规则判定用精确匹配即可表达本题的全部风险口径 |
| 并发控制 | 单机演示，草稿存储是单个 JSON 文件 |

## 4. 成功标准总表

这一张表是后面 `docs/03-evaluation.md` 的对照基准。

| 编号 | 成功标准 | 判定方式 |
|---|---|---|
| **C1** | 六个必验点全部有真实模型产出的运行记录，另有 Mock 版本便于零配置复现 | `examples/real_llm/` 下 7 个目录齐全 |
| **C2** | 存在 ≥2 条**动作序列不同**的路径，且差异由工具返回驱动 | 测试 + `case02` / `case04` 的 trace 对比 |
| **C3** | trace 五项字段齐全，且不落模型完整思维链 | `ToolCallRecord` schema + 测试断言长度上限 |
| **C4** | 预算上限生效且返回明确未完成状态 | 测试 `test_step_budget_*`；CLI 退出码 `2` |
| **C5** | 不可能越权发布 | 工具注册表断言 + 最终答复文本扫描 |
| **C6** | 不可能虚报保存成功 | 最终 `draft_status` 只认工具返回结果，不听模型自述；另有注入失败测试 |
| **C7** | 重复提交只产生一份草稿 | 幂等测试 + `case05` |
| **C8** | 无 Key 也能复现全部流程 | `examples/mock/` + 68 个测试无需 Key |
| **C9** | 上述每一条都有可执行命令复现 | README 的"30 秒跑起来"与验收点命令表 |

## 5. 关于「AI 辅助」的立场

这个项目的每一行代码都由我 review 过，但我用 AI 辅助生成了初稿，并且**保留了踩坑记录**。
之所以连"AI 写出了什么坑"都写进文档，是因为这道题明确提到要看"主动学习与改进能力" ——
能否发现自己没写过的那段代码在想什么，比能否独立写出全部代码更接近考察目标。

范围详见 `docs/04-ai-usage.md`。
